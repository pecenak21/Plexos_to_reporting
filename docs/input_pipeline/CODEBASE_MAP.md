# Codebase map — session 0 (`/orient`)

Written before any input-pipeline code exists. Purpose: what the reporting engine already gives us — conventions, reusable pieces, and traps — before sprint 1 starts. Re-read `docs/input_pipeline/PROGRESS.md` alongside this; that file has the per-story verdict, this file has the reasoning.

## 1. Layout and conventions, in about a page

**Language/env.** Python 3.12.8 (conda env `py312`, confirmed via `python --version` in that env). Windows only; `run_report.bat` and `src/testing_pleoxs_input.py` hardcode `C:\Users\cto\...`. Data lives on network drives (H:/F:) for the reporting engine; the input pipeline's sample data lives inside the repo instead (`docs/sample model/`, `docs/sample APS source files/`).

**Package layout.** `src/` is flat — eight scripts, no sub-packages, no `__init__.py`. They import each other by bare module name (`from database import ...`, `from transformers import (...)`), which only works because `create_reports.py` is always run with `src/` as the working directory / on `sys.path` (via `run_report.bat` invoking the script directly). This bare-import style does not extend to a nested package — `src/plexos_input/` will need proper relative or absolute-package imports and cannot copy this pattern.

**Dependency management.** `requirements/requirements.txt` pins three packages: `duckdb==1.5.4`, `numpy==2.5.1`, `pandas==3.0.3`. Checked against what's actually importable in `py312`: `duckdb` matches (1.5.4), but `numpy` is actually **1.26.4** and `pandas` is actually **2.2.2** — the pinned file does not describe the real environment. `openpyxl` (3.1.5), `eecloud` (1.5.2889.510), `pytest` (8.3.2, plus `pytest-repeat`/`pytest-xdist`) and `ruff` (0.8.4) are all already installed in `py312` but **not listed in `requirements.txt` at all**. `plexos_sdk` is **not installed** — confirmed by `ModuleNotFoundError` and a repo-wide grep of `site-packages` for `class PLEXOSSDK` (no hits). This is a hard blocker for CDM-01 onward; see §4.

**Tests.** No `tests/` folder, no test framework wired into the repo (though `pytest` happens to be installed on this machine already). `src/standard_integration_testing.py` compares generated CSV reports against baseline CSVs in `docs/Baseline Reports/` — it validates report *output*, not code; it is not a pytest suite and has no assertions library, just pass/fail diffing.

**Entry points.** One: `run_report.bat` → `python src/create_reports.py <workbook>.xlsm`. No CLI framework (no `argparse`/`click`), no subcommands. `execute_pipeline(config_path)` is the only orchestration function, called from `if __name__ == "__main__"`.

**Config/logging.** Configuration is 100% Excel-driven — `create_reports.py:load_excel_config` reads `pd.ExcelFile`, pulls typed sheets (`Blueprint_std`, `Blueprint_rat`, `Groups`, `Summary` as a key/value index, `UnitConversion`, `Generator_name_map`, `Contract_name_map`), normalizes headers with `.str.strip().str.title()`, and fills any missing optional column with `''`. This key/value-sheet-via-`index_col=0` pattern is the closest existing analogue to WBK-01's Run sheet reader. There is no logging module anywhere — all diagnostics are `print()` with hand-rolled prefixes (`[+]`, `[-]`, `[!]`, `[~]`, `[?]`). `exceptions_report.py` is the one structured exception-collection mechanism: severities (`ERROR`/`WARN`/`INFO`), de-duplication by (severity, category, message) with an occurrence counter, written to `Exceptions_Report.log` at the end of a run.

**Coding style.** No type hints anywhere in `src/`. No docstring convention beyond occasional module/function docstrings explaining *why*, not *what* (e.g. `database.py`'s comment on why `_lookup_db_unit` is cached). Comments favor rationale over restatement — matches this project's own comment guidance. No linter currently enforced (ruff is installed but nothing is configured or run against `src/`).

**Windows-specific.** Path separators are hand-normalized in several places (`str(base_dir).replace('\\', '/')` in `database.py` and `create_reports.py`) because DuckDB's `read_parquet(glob)` wants forward slashes even on Windows. The input pipeline's byte-for-byte path preservation rule (CLAUDE.md rule: preserve backslashes/casing in stored paths) is the opposite requirement in the opposite direction — reporting code normalizes for its own glob reads; the input pipeline must **not** normalize the paths it writes into the model.

**Third-party usage today:**

- **PLEXOS Cloud CLI** (`plexos-cloud.exe`) — used by `convert_zip_to_parquet.py` for `solution convert zip-to-parquet`, invoked as a list-form `subprocess.run(..., check=True, capture_output=True, text=True)` (no shell=True — good precedent). Installed on this machine at `C:\Users\cto\AppData\Local\Programs\PLEXOS.Cloud\plexos-cloud.exe` and resolvable via `shutil.which`, but `find_plexos_cli`'s hardcoded fallback search dirs do **not** include the actual install location (see §3) — they would fail on a clean machine that relies only on the fallback. The `cloud_cli_path` environment variable that `testing_pleoxs_input.py` and the reference docs expect is currently **unset** on this machine.
- `eecloud` (`CloudSDK`) — used only in the scratch file `src/testing_pleoxs_input.py`, which is a job-worker template (`--input-path` CLI arg, reads `cloud_cli_path`/`simulation_path`/`output_path` env vars). This is Energy Exemplar's cloud-job harness, a different thing from `plexos_sdk`'s local `PLEXOSSDK` class — do not conflate the two when writing OPS-01's environment check.
- **Reference material** (`docs/input_pipeline/reference/README.md`'s table, unfilled) — confirmed present and reachable this session at `C:\Users\cto\PLEXOS-Cloud-Automation-Scripts` (outside this repo; needs `/add-dir` in a story session): `Documentation\PLEXOS_SDK_Methods.md`, `Documentation\CloudSDK.md`, `Documentation\PLEXOS_SDK_Examples.md`, `Documentation\PLEXOS_SDK_TLDR.md`, `Documentation\Duckdb_Solution_Queries.md`, `Pre\PLEXOS\ReplaceModelInputFiles\README.md` (WRT-01/WRT-04's name-resolution pattern), `tests\post_test_query_write_memberships.py` (CDM-04's cross-check), `Automation\PLEXOS\TimeSeriesComparison\timeseries_comparison.py` (DIFF-05). `Task2_D3_Problem_Definition.md` was not found by name in that repo. The README's path table is still blank — worth filling in before OPS-01/CDM-01/WRT-01 need it, but that file is outside this session's write scope.
- **DuckDB** — used extensively in `database.py` and `create_reports.py`, but always over **Parquet solution output** (`mem_fki`, `mem_period`, `v_data` — PLEXOS's own zip→parquet export schema), never over a model `.db`. No direct `openpyxl.Workbook`/`load_workbook` usage exists to borrow from for WBK-05's validation/error-reporting story (which will likely need cell-level access openpyxl gives that pandas doesn't).

## 3. Existing code that conflicts with a non-negotiable rule

None of these are *live* violations of the input-pipeline rules — the reporting engine never touches a model `.db` and the input pipeline doesn't exist yet — but they are the exact anti-patterns CLAUDE.md names, and each is a live example a future `/story` session could be tempted to copy if it greps `src/` for "how do we already do DuckDB/Excel/CLI here."

- **Module-level default DuckDB connection + global mutable state**, conflicting with Rule 5's "per-call, read-only" requirement and CDM-02's explicit contextmanager design (`open_model`): `src/database.py:16` (`_db_initialized = False`, module global), `src/database.py:18-36` (`initialize_database_structures` — mutates the global, uses the bare `duckdb.query(...)` default connection rather than an explicit per-call connection), `src/database.py:39-46` (`@functools.lru_cache(maxsize=None)` on `_lookup_db_unit` — a second piece of unbounded global state keyed by `base_dir`).
- **f-string SQL** built by directly interpolating caller-supplied values into the query text, conflicting with the spirit of Rule 7 (natural-key matching, `IS DISTINCT FROM`) even though these specific queries don't touch a model `.db`: `src/database.py:44` (`f"SELECT unitValue FROM mem_fki WHERE LOWER(TRIM(propertyName)) = '{lookup_prop_lower}' LIMIT 1;"`), `src/database.py:103-158` (the whole `pivot_query` built via string-joined `sub_conditions`).
- **Hardcoded absolute paths**, conflicting with "New code must not hardcode absolute paths": `run_report.bat:2` (`"C:\Users\cto\PlexosReorting\src\create_reports.py"`), `src/testing_pleoxs_input.py:6` (`target_directory = r"C:\Users\cto\PLEXOS-Cloud-Automation-Scripts"`).
- **No `.gitignore` exists anywhere in the repo.** This is the sharpest live risk, not just a style anti-pattern: `git status` at session start shows `src/__pycache__/*.pyc` as tracked, modified files, and the untracked sample folders (`docs/sample model/`, `docs/sample APS source files/`) currently rely entirely on nobody running `git add -A`/`git add .` to stay uncommitted. CLAUDE.md's "never commit anything under docs/sample model" rule has no mechanical enforcement right now.
- **CLI fallback search paths that don't match this machine's real install**, not a rule violation but worth flagging next to OPS-01's environment check: `src/convert_zip_to_parquet.py:46-51` searches three `...\Energy Exemplar` directories (`Program Files`, `Program Files (x86)`, `LocalAppData\Programs`); the actual install is `C:\Users\cto\AppData\Local\Programs\PLEXOS.Cloud\plexos-cloud.exe` — a different leaf folder name (`PLEXOS.Cloud`, not `Energy Exemplar`) in all three cases, so none of the three fallback dirs would match even though the third one is close. It resolves today only via `shutil.which` (PATH). A machine without it on PATH would fail `find_plexos_cli`'s fallback despite having the CLI installed.

## 4. Anything reusable the backlog would otherwise rebuild

- **Excel key/value sheet reading** (`create_reports.py:49-54`, the `Summary` sheet via `pd.read_excel(xl, 'Summary', index_col=0)` then `.loc[key, 'Value']`) — worth reusing as the idiom for WBK-01's Run sheet, adjusted for case-insensitive/whitespace-tolerant key matching and the "unknown key" error WBK-01 requires.
- **Structured exception/exception-ledger pattern** (`exceptions_report.py` in full) — the severity levels, de-duplication-with-count, and `record()`/`reset()`/`write()` shape are a solid starting skeleton for BLD-08's exception ledger and could plausibly be extracted into a shared module rather than reimplemented, provided the new version drops the module-level `_entries` global in favor of an instance passed through the build.
- **List-form `subprocess.run` against the Cloud CLI** (`convert_zip_to_parquet.py:100-111`) — correct pattern (list args, `check=True`, `capture_output=True, text=True`, catches `CalledProcessError` and surfaces `e.stderr`) for CDM-01's `ensure_db` shelling out to `plexos-sdk xml-to-db`, and already demonstrates "pass the CLI's own stderr through" which is Rule 14.
- **`shutil`/`Path`-based directory existence + rebuild logic** (`convert_zip_to_parquet.py:66-98`, the "already-converted output dir short-circuits, a partial one is rebuilt" logic) — a reasonable shape to look at (not copy verbatim, since the input pipeline's rule is "always regenerate the `.db`, force by default" rather than "skip if present") when writing BLD-03's copy-model-and-tree-forward.
- Nothing else rises to "would otherwise be rebuilt" — the domains (Parquet solution output vs. a model's SQLite-backed `.db`; RTSim-format pivot reports vs. a flat build report/diff workbook; zip-to-parquet conversion vs. xml-to-db conversion) are different enough that most of `src/` is precedent-by-analogy rather than literally reusable code.

## 5. Confirming the proposed package layout

CLAUDE.md's proposal — new code in `src/plexos_input/` (a real package, not a flat script folder), tests in `tests/` (pytest) — is confirmed as the right call. Nothing in the existing `src/` layout (bare-name imports, no `__init__.py`, no test folder) is worth preserving into the new code, for the reasons in §1. `pytest` and `ruff` are already installed in `py312` even though unpinned; a nested `src/plexos_input/` package will need either a `pyproject.toml`/`setup.cfg` for editable install or explicit `sys.path` handling in `tests/conftest.py` — OPS-01 needs to decide which, since nothing in the current repo does either (the flat `src/` layout works today only because scripts are run directly with `src/` as the working directory).
